# Marketing message unsubscribe

A marketing recipient can stop mail for the brand that received their signup. The native confirmation form works without JavaScript, Clerk, a paid subscription, cookies or access to the sending worker. GET and HEAD have no database effects. POST accepts exactly one `List-Unsubscribe=One-Click` field as URL-encoded or multipart form data, with a 4 KiB uncompressed request limit. The endpoint accepts origin-less mailbox requests and intentional same-origin form submissions. Foreign browser origins are refused, and the response never redirects or identifies a subscriber. [RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html) · [RFC 2369](https://www.rfc-editor.org/rfc/rfc2369.html)

## Configure and retain links

Keep the opt-out service at the exact HTTPS `APP_ORIGIN` used when the message was created. Set `FLOCKLETTER_UNSUBSCRIBE_BINDINGS` to a JSON array of 1–64 explicit workspace and brand pairs using `workspaceId` and `brandId`. Retain each issued binding even when a brand pauses intake, loses access or stops sending. The opt-out handler does not consult those gates. Removing a binding or its recipient records removes the ability to resolve its links, so recovery and data-lifecycle jobs must preserve applicable suppression obligations.

Only a trusted worker that issues messages needs `FLOCKLETTER_UNSUBSCRIBE_SIGNING_KEY`, a dedicated random 32-byte hex key. Use a key separate from the confirmation signer. The public handler can redeem issued links with just the binding map. Replacing the signing key gives future messages new links. Existing capabilities keep working through their stored digests. Losing both the bindings and the protected database requires restoring them before enabling delivery.

After the worker has authorized a specific recipient, `buildMarketingMessageLinks` rechecks their confirmed state inside the existing brand transaction. It returns the visible body URL, one angle-bracketed HTTPS `List-Unsubscribe` value, the `List-Unsubscribe-Post` value, and the two header names that the eventual provider must cover with DKIM. Retrying for the same confirmed contact on the same origin and key returns the same link. The private row contains a random ID and SHA-256 capability digest. The URL carries no email, subscriber ID, workspace ID or brand ID.

The canonical suppression operation records one consent transition, invalidates unused confirmations and cancels unattempted confirmation jobs. A complaint or hard bounce keeps its stronger state. A legacy record without original consent evidence receives a factual marketing-link opt-out event. Invalid, previously used and newly accepted tokens have the same public result. GET and HEAD set strict-origin so a native browser sends the exact Origin but never includes its path or query in referrers. Receipts set no-referrer. All responses use no-store, no-index and a restrictive same-origin content-security policy.

## Verification and live gates

Run `npx vitest run tests/marketing-unsubscribe.test.ts tests/subscriber-intake.test.ts` against a disposable database. The integration suite exercises both form encodings, repeated and concurrent requests, a paused brand, missing signing keys, key rotation, tamper attempts, colliding subscriber IDs across workspaces, legacy consent, restricted SQL privileges, and rejection of browser forgery, duplicate fields, files, compression and over-limit requests. The tests use fictional addresses and construct the header values privately. Campaign sending stays disabled.

Run `node --import tsx scripts/prove-marketing-unsubscribe.ts` with the Playwright Chromium browser installed. The test starts its own loopback HTTPS application and database, trusts its temporary TLS public key only in the fixture browser, and submits the native form with JavaScript disabled. It checks scanner-safe GET, successful same-origin POST and that even asset requests carry at most the origin as a referrer. Use `FLOCKLETTER_BROWSER_CHANNEL=chrome` for installed desktop Chrome.

Before a real marketing message, inspect a delivered message from the actual provider, verify its sender’s valid DKIM signature and both header entries in the signature's `h=` list, and exercise the opt-out in an approved mailbox. The RFC requires the capability in the HTTPS URI. Configure and verify query redaction on the reverse proxy, Render request logs, tracing, exception reporting, analytics and click-tracking rewrites before any real tokens are issued. The application writes no token to diagnostics and sets no referral or tracking links. Provider signing and infrastructure log redaction have not been verified.
