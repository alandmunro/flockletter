# Single-recipient test-send playbook

D-047 accepts the bounded policy for FL-CAM-010, FL-CAM-003/005/006/007, FL-USG-001/002 and FL-API-001/003. The source implementation uses the canonical contracts described below. Integration, staging and live-provider verification are recorded separately; this policy record does not activate mail.

A test uses exactly one existing confirmed contact in the selected saved campaign’s brand. The workspace shares a ceiling of five approved test requests per UTC day across every brand; failure, rejection or cancellation does not refund that daily admission. Accepted real tests use one recipient-email allowance unit, including trial limits, and no monthly campaign slot. Existing photos and commerce settings are preserved.

1. Inspect the saved campaign and resolve its content, service, sender and provider gaps before gathering a test target. Keep all original image references and the meaningful plain-text alternative.
2. A current owner uses the existing brand audience directory to select a confirmed contact. An email search is a lookup, never a new subscriber or permission to send to an arbitrary address. Delegated callers use only a known, authorized same-brand subscriber reference; they do not acquire private audience-directory access.
3. Request a separate immutable test review. Show the saved version, sender identity, selected recipient, timing, mode and applicable daily/recipient allowance. This is not a review or approval of the full campaign.
4. Obtain explicit approval of those frozen facts before requesting a test transmission. Preserve the original operation key and inputs when reconciling a lost acknowledgment. Changed content, sender, recipient or eligibility requires a fresh review.
5. Read the original outcome. Provider acceptance is not inbox delivery, capture is not real provider evidence, and an uncertain attempt may already have reached the provider. Use safe status lookup/reconciliation; never create a new send to work around an unknown result or daily cap.

Tests are immediate, with no future scheduling. New submission attempts expire at midnight UTC at the end of the approval day; unknown outcomes remain available for reconciliation without another submission. Pending or uncertain work must retain the reservations needed to prevent concurrent cap bypass. Cancellation stops unattempted work and cannot recall an accepted message. Normal service, sender, current authority, consent, suppression, hold, provider, rate and usage checks apply again before submission. A test is not a route around them.

Staging exercises capture messages with synthetic data. Live transport requires its existing separate credentials, configuration, recipient authorization and release evidence. Production credentials alone do not establish verified delivery. The approved canonical API contract is below. Source-level checks do not establish hosted activation or live-provider acceptance; do not invent a parallel transport or bypass these commands.

## MCP sequence

Use a current brand-scoped connection with `read` and `campaign:send`; additional permissions retain their ordinary meaning. The owner supplies the known subscriber reference from the authorized, confirmed brand directory. A delegated connection does not gain `audience.list`, `audience.contact` or the owner-only `delivery.testDetails` command. Restricted preflight information is not permission to fetch a private directory or bypass a gap.

1. Read `campaign_get` and retain the exact saved `version`. Call `delivery_preflight` with `brandId`, `campaignId`, `expectedVersion`, `purpose: "test"` and the one known `subscriberId`. Do not include a group or `dueAt`. Resolve its test-specific gaps; the full-broadcast audience size or campaign-slot allowance must not substitute for the one-recipient test checks. The daily budget is a snapshot, rechecked at approval.
2. Call `delivery_reviewTest` with a stable `operationKey` and those same campaign/brand/version/subscriber fields. Compare the returned `purpose`, one-recipient count, version and known-input subscriber echo. Present the frozen subject, sender, recipient and immediate timing for explicit approval. The returned review is not authority to send a broadcast.
3. After explicit approval, call `delivery_approveTest` with a new stable `operationKey`, the same `brandId`, returned review `id`, frozen `expectedVersion` and original `subscriberId`. Generic `delivery_approve` is not a substitute and rejects test reviews. Each newly approved request consumes one daily admission even if later canceled or rejected; an identical operation replay does not create another admission.
4. Read `delivery_report` with `brandId` and `id`. The worker processes admitted work; `delivery_process` with its own stable operation key requests bounded processing or reconciliation of that same test. Never create a fresh review to conceal an unknown result. `delivery_cancel` stops unattempted work and preserves unknown/accepted outcomes. A late reconciliation does not extend the approval day’s new-attempt window.
5. Generic list/report views omit private subscriber references. The reviewing caller retains the ID it originally supplied. A browser owner can reopen the exact saved test through `delivery_testDetails`; a delegated connection cannot use that owner-only recovery path. Captured message inspection uses the existing owner-only `delivery_message` route and is not live-provider evidence.

If a response is lost, retain its exact operation key and payload. Retry/reconcile the original intent; do not create a second approval key to work around a daily limit or uncertain send. Revoked authority, expired grants and changed campaign/sender/consent require their normal resolution, not a new bypass. Never place customer addresses, tokens or message bodies in a public playbook or commit.

## Browser operation and local evidence

On Delivery, choose the saved campaign, then use **Test one confirmed contact**. The picker lists only the current brand’s confirmed contacts; it has no default recipient and exact-email search only looks up existing records. Review shows the frozen test facts before a distinct **Approve one-recipient test** action. An unknown approval retains the same operation key/payload and blocks a replacement in that view. Owner-only saved details recover the original review; completed tests do not offer a new approval.

Test history uses `delivery.list` with `purpose: "test"`; normal campaign history uses `purpose: "broadcast"`. Keeping these bounded views separate prevents routine test traffic from crowding the latest 100 campaign records. A paused test has **Resume unchanged test**, which calls `delivery.resume` for the same ID and verifies the returned original day/version. The server repeats the current-day and normal eligibility checks. Canceling never refunds daily admission or recalls accepted mail.

The focused local proof is [prove-customer-test-send.ts](../../scripts/prove-customer-test-send.ts). It uses synthetic local identity, genuine scoped PostgreSQL records, captured signup/confirmation and an injected offline renderer. It exercises explicit selection/review/approval, no submission at review, a lost approval response retried with identical inputs, one daily admission, zero campaign slots, original inline photo rendering, unchanged saved subject/assets, completed-review recovery and desktop/390px layouts. These captures prove the UI and durable exercise path, not a real provider or inbox.
