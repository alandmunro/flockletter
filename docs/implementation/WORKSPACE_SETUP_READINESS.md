# Truthful workspace setup and sender refresh

This implements FL-ONB-001/002/004, FL-DEL-002 and FL-API-001. The overview reads canonical `workspace.preflight` instead of treating every paid account as pending and every live-delivery configuration as upcoming. The response separates service access, renderer configuration, delivery mode, per-brand sender identity/verification and confirmed audience observations. It includes a database-clock observation time and named next actions. `canSend` stays false and `reviewRequired` stays true: no setup observation authorizes a campaign.

The owner shell fetches this read command with loading, unknown, error and refresh states. A failed or pending refresh hides prior verified observations. Current Stripe service facts come from the same internal subscription eligibility calculation used by delivery. An exercise remains labelled as an exercise; a configured mode alone never proves sender verification or inbox delivery. Counts describe confirmed contacts, which still undergo consent and suppression checks during exact review and execution.

Detailed service state and allowance are returned only to a currently verified owner session. Other callers receive null, rather than billing details or inferred paid access. Confirmed audience totals require an owner session or an explicit `audience:summary` connection grant; ordinary read grants receive null and a generic review instruction. Connections are rechecked against the persisted read grant, current issuing-owner authority, expiry and revocation; audience-summary permission comes from that current record, and its brand IDs are intersected with the authenticated actor’s scope. Brand restrictions apply before any brand observations are returned. Member overview retains its preparation interface and does not acquire owner commands. HTTP and MCP use this same canonical response.

Sender identity saves recheck authoritative sender status; an unavailable check does not undo the saved profile or imply verification. Manual refresh retains unsaved field edits and clears stale success. Workspace setup observations do not hydrate or deactivate provider route caches; an unloaded route stays unverified until its normal setup/worker path loads it. Infrastructure refresh disables brand selection while reading and checks request/brand identity before applying a reply, so a late response cannot overwrite a different selected brand. These reads grant no new provisioning or sending authority.

Validation uses disposable PostgreSQL and synthetic browser fixtures: current service versus configuration, restricted read and audience-summary grants, owner revocation, error/retry, per-brand observations, saved and unsaved sender fields, guarded infrastructure refresh, and desktop/390px layouts. It does not establish hosted provider credentials or live mail verification.

The local model drafted onboarding presentation and SSR test scaffolding. Chat corrected an incorrect workspace-brand source, missing baseline steps, malformed definition-list rows, widened fixture types and a weak error assertion; much of the initial presentation draft was replaced to preserve the existing visual layout and strict observed-fact semantics. Chat owns permissions, canonical integration, asynchronous lifecycle handling, browser proof and acceptance review.
