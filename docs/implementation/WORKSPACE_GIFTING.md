## Funding and provider review

Tremendous uses `https://testflight.tremendous.com/api/v2` in sandbox and `https://api.tremendous.com/api/v2` in production. The sandbox has a replenishing simulated balance and omits some partner redemption steps. Production requires a separate account, an application through **Team settings → Developers**, and Tremendous compliance approval. [Environments](https://developers.tremendous.com/docs/sandbox-environment) · [Production access](https://developers.tremendous.com/docs/production-api-access)

The workspace adapter selects the documented production API origin only in explicitly enabled live mode. [Workspace adapter](../../src/server/workspace-gifts/provider.ts)

## Reconcile a claim or payment

1. **Claim.** Confirm eligibility and the reviewed product set against `GET /products?country=US&currency=USD`. Persist intentional claim before submission. Read `GET /orders/{offer_id}` by external ID before attempting `POST /orders` with the same offer ID and immutable terms. On timeout, conflict, outage or review, hold the reservation and look up again. On verified `EXECUTED`, match recipient, value, currency, order and LINK reward before consuming credit once. Inspect failed/canceled attempts by provider order ID. A revisit uses `POST /rewards/{id}/generate_link`. Earlier links remain valid. Keep links and claim tokens out of evidence. [Create](https://developers.tremendous.com/reference/create-order) · [Lookup](https://developers.tremendous.com/reference/get-order) · [LINK delivery](https://developers.tremendous.com/docs/link-delivery)
2. **Events.** Tremendous permits one HTTPS receiver per organization, configured with `POST /webhooks`. Preserve any existing receiver. Verify the raw-body `Tremendous-Webhook-Signature`, durably deduplicate by `uuid`, acknowledge with 200, then retrieve the resource. Watch order approval/cancellation, top-up credit/reversal and funding events. Single-reward API failures may be synchronous. LINK rewards have no delivery-success webhook or proof of store redemption. [Webhook API](https://developers.tremendous.com/reference/create-webhook) · [Events and retries](https://developers.tremendous.com/docs/webhooks-1)
3. **Stripe test scope.** At `https://api.stripe.com/v1`, verify `GET /account` against the expected test account. Its test key needs account and charge reads, PaymentIntent creation/confirmation and lookup, and refund creation/lookup. The fixture uses `POST /payment_intents` and `POST /payment_intents/{id}/confirm`. Match `GET /payment_intents/{id}` to the purchase, USD, received amount and `livemode=false`. For closure, look up `GET /refunds?payment_intent={id}` before `POST /refunds`. Match `GET /refunds/{id}` and `GET /charges/{id}` to the original payment. A workspace Checkout journey also needs its paid `GET /checkout/sessions/{id}` binding. Verify raw-body `Stripe-Signature` with the test endpoint’s signing secret and deduplicate event IDs. Exercise duplicate and out-of-order payment, refund and dispute events. Retrieve `GET /disputes/{id}` before changing disputed credit. The fixture confirms settlement by API lookup. Signed event delivery needs its own evidence. Test money never moves between banks. [Fixture adapter](../../src/server/gifting-providers.ts) · [Stripe testing](https://docs.stripe.com/testing) · [Checkout](https://docs.stripe.com/payments/checkout/fulfill-orders) · [Webhooks](https://docs.stripe.com/webhooks) · [Disputes](https://docs.stripe.com/api/disputes/retrieve)
