# Workspace and operator workflows

## Audience groups and campaign review

In **Audience**, choose a brand, create a named group and add existing contacts by email. Removal from a group preserves those contacts and their consent history. A group can include pending or suppressed contacts. The directory shows separate counts for each subscription state. Owners can create up to 50 groups per brand and change up to 250 addresses at a time. An unrecognized address rejects the whole change and identifies the affected row. A scoped connection with `audience:summary` can request aggregate counts for a known group in its brand.

In **Campaigns**, review the saved draft for either the test mailbox or confirmed synthetic recipients. For a confirmed audience, choose a group to narrow the selection. The review records the group name, exact recipients, rendered content, version and original image digests. Moving or deleting a group does not change the review. Saving new campaign content invalidates an outstanding review. At capture time the worker rechecks suppression, current membership, access, grants and reserved capacity. Select **Schedule for later** and supply a future local time to queue a scheduled rehearsal. An unfilled date is an error. A queued item remains in PostgreSQL across a restart. Free Render services can sleep. Due items are picked up after the bound worker is running again.

## Workspace, billing and support

- **Team** shows members from the current Clerk organization. The owner grants viewers and editors access to specific brands. A viewer can preview, an editor can save changes, and the owner manages groups, connections, billing and approvals. [Team access](TEAM_ACCESS.md)
- **Workspace** displays company and brand limits, sandbox billing status, and an account retention preview. Verified cancellation with an effective end time starts the 90-day clock. Reinstatement clears the preview. The preview does not purge records. The policy for permanent erasure, backups, minimal retained records and exceptions is O-009.
- A signed Stripe test event plus a current provider lookup must establish an expired checkout with no customer, subscription or trial before a new checkout can be started. The owner can restart that exact attempt. Its archive retains the old provider identity and the verified observation. A repeated restart reuses its successor. An ambiguous result, canceled subscription or occupied customer goes to reconciliation. The sandbox limits restarts to five per workspace in a rolling 24 hours. Complimentary workspaces bypass Stripe. [Staging billing and sender setup](CAMPAIGN_PILOT.md)
- **Help** at `/help` contains plan, trial, unsubscribe and capture guidance with an email contact. An operator with the local `llm` command can run `npm run support:draft -- plans` (or `trial`, `audience`, `campaigns`). Only reviewed public facts for the selected topic reach that model. Compare the draft with the returned approved facts before using it. The draft includes a disclosure of AI assistance. Topics involving billing cases, recovery, privacy, security and unknown questions return a human handoff without contacting the model. The command has no inbox or mail transport. Automatic external replies and support retention remain O-012.
- Operators can perform the isolated two-workspace recovery exercise in the [self-hosting guide](SELF_HOST.md). It demonstrates the difference between a successful database restore and a recovery which preserves the latest known unsubscribe.

## Verification

The billing integration tests cover signed webhooks, duplicate restart requests, uncertain provider outcomes, historic receipts, stale events and isolation. The database and browser suites exercise the real Flockletter APIs, PostgreSQL roles, tenant restrictions, group operations and owner/member views with fictional data. Full release acceptance still requires live-provider and commercial evidence. The staged workflow records only synthetic captures. See [traceability](../TRACEABILITY.md).
