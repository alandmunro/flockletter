# Explicit temporary no tax collection

Requirements: FL-BIL-002/003/004/006/007, FL-PROD-004, FL-API-001 and FL-OPS-003/004/007. D-062 records the owner's explicit temporary Flockletter-only collection instruction. It does not declare the service/customer exempt or resolve the open tax question. Code approval does not install configuration or activate billing.

## Configuration and scope

New live agreements require exact `FLOCKLETTER_BILLING_TAX=off` or `stripe-automatic`; absent, empty, `false`, misspelled and unsupported values fail closed. `off` is supported in Stripe test/staging and production. Billing still requires its ordinary dedicated account/key/catalogue/card/portal/webhook settings, production/live approval, verified trial registry/history, exact customer acceptance and release checks. Pro enrollment stays paused and FFA's Growth grant remains independent of Stripe.

The off policy applies to new Flockletter agreements, not the merchant account. It explicitly disables automatic tax on paid Checkout and trial subscription creation, requests no manual rates, and verifies returned subscription/item/default rates and invoice tax totals before accepting those facts. Direct subscription creation explicitly clears its own default rates. Checkout's create schema accepts only a rate array; its empty array is omitted by the installed SDK, so no unsupported clear value is sent there. Provider responses must still prove no manual or automatic tax. Exclusive USD catalogue amounts, Flockletter tags and the existing business SaaS product code remain verified. A same-amount price from another application is insufficient.

Card setup remains setup-only, requires a complete provider-held US billing address and collects no subscription charge. Exact trial review includes collection mode, monthly price, first-charge date, current policies and verified location. The owner explicitly accepts that frozen review. Direct paid/rejoin/restart commands similarly require the current server-reported tax mode; UI/API/MCP use the same command schemas. The customer sees “no tax collected” for off-mode acceptance. No customer `tax_exempt` field, registration, global tax default or other application's setting is changed.

## Managed Payments and provider facts

Both supported Checkout modes explicitly send `managed_payments[enabled]=false`, preserving the merchant-wide default. Setup mode does not receive unsupported automatic-tax parameters. The installed Stripe 23.1.0 SDK and the inspected 2026-09-30 create-subscription schema do not expose a writable Managed Payments parameter on direct `Subscriptions.create`; do not bypass the types to invent one. Returned managed-enabled subscriptions fail verification. A no-tax subscription must prove disabled/null Managed Payments, disabled automatic tax, empty manual rates and no invoice tax. Missing proof or an unexpanded invoice remains unresolved.

See Stripe's [Checkout creation reference](https://docs.stripe.com/api/checkout/sessions/create), [subscription creation reference](https://docs.stripe.com/api/subscriptions/create) and [invoice object](https://docs.stripe.com/api/invoices/object). No account-wide setting is changed to work around a provider rejection. A failure after a durable mutation remains an unknown outcome to reconcile; it is not permission to POST again, cancel an agreement or issue a refund automatically.

## Safe policy changes and rollout

1. Keep new billing off while promoting a reviewed code/configuration pair through staging. The web and worker must use matching revisions, mode, account and stable trial-history keys. Run the read-only billing inspector with the intended explicit collection policy.
2. Inventory saved trial reviews, approved activations and paid/rejoin Checkout intents before changing mode. Unaccepted trial reviews require a fresh review if mode changes; verification happens before consuming lifetime eligibility. Public policies are versioned, and changed review hashes clear the checkbox.
3. Accepted/unknown activations retain their original saved mode and stable operation key. Read-only lookup and signed events reconcile that original agreement. Current-mode acceptance is checked before inserting a fresh paid/rejoin intent, while retries validate the original saved hash before lookup; an unchanged accepted tax-mode payload can therefore still reconcile after a mode switch. They never create a replacement under a new mode. Historical accepted subscriptions are not rewritten by changing the environment setting.
4. A saved open paid Checkout in a different mode is held without returning its bearer URL or creating a replacement. Resolve the original operation through support. Only authoritative terminal expiry and explicit acceptance of current terms permit the ordinary restart path. Do not reset intents, trial claims or usage to make the new policy appear fresh.
5. Exercise both card-funded trial activation and direct paid Checkout in the real sandbox. Verify actual disabled automatic tax, no manual tax/default/item rates, zero invoice tax, disabled/null Managed Payments, exact amounts, current US address and signed events. Exercise an uncertain response and a mode change. Intercepted SDK tests do not establish those external facts.
6. After staging/provider verification, the operator may install the intended production policy and follow the ordinary promotion/activation controls. This PR performs no Stripe/Render changes, deployment or merge. Removing the explicit live policy prevents new billing rather than selecting a silent default. Preserve event receipt credentials and reconciliation when billing is off.
