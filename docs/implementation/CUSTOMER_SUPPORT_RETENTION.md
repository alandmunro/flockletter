# Customer support and account retention

D-042 implements FL-SUP-001/002, FL-ID-005, FL-ONB-004, FL-API-001/003 and FL-OPS-005/006 through the same tenant commands for the owner UI, HTTP and MCP. Staging uses explicit captured exercises. No external support messages or hosted erasure are activated by this change.

## Support conversation

The workspace owner opens Support, selects a topic and supplies a subject and plain-text question. The durable conversation records incoming content, revisions, reviewed replies and their provenance. Security, privacy, recovery, refunds and other uncertain requests are escalated. Receiving signed email never grants membership or permission to change an account.

In the captured exercise, the owner can prepare an answer from approved public product guidance, edit it and approve its exact saved version. Local AI assistance receives only that public guidance. Incoming questions, tenant information, subscriber addresses, secrets and message history are excluded from its prompt. A reply with `approved_guidance` provenance uses the product facts directly; it is not described as AI-generated. `ai_assisted` identifies a locally drafted answer. Replies remain human-reviewed; automated-send policy and provider data-use approval remain prerequisites for activation.

Approval persists an immutable dispatch before transport. Capture records the actual dispatcher outcome in PostgreSQL without sending email. Live mode requires a separately verified support operator, dedicated sender and provider. An attempted request whose acknowledgement is lost remains uncertain. Restart/reconcile looks up the provider receipt and does not guess or submit a second message. At most five replies are dispatched per conversation; automatic replies are ignored by intake. Each workspace is bounded to 500 conversations and 5,000 inbound events. A scheduler calls `CustomerSupport.tickWorkspace(workspace)` using the original durable reply approver and freshly verified owner/operator authority; no customer command accepts operator identity supplied by the browser.

The optional fixed-host Resend adapter uses a dedicated server credential, provider idempotency keys, an eight-second timeout and redirects disabled. Provider acceptance is not a delivery claim. Native inbound providers must normalize authenticated events into the strict configured email envelope before signing the internal adapter event; its verified destination and workspace come from server configuration. Unknown providers, missing verification and missing sender settings fail closed. Current signed-envelope handling is tested with synthetic signatures, not an external-provider delivery claim.

## Retention review

The Billing domain supplies a verified service-end fact, source and version. Complimentary, active and reinstated accounts have no eligible purge date. Retention begins at the actual effective service end, then waits 90 days. Inspection inventories every managed public tenant table from the reviewed runtime manifest and records the inventory digest. Schema drift prevents execution. Service facts are rechecked under the workspace lock; a hold cancels pending execution requests. Newer billing facts cancel obsolete cases.

The owner reviews the inventory and may request a due case. This creates a durable job awaiting a separately authorized operator. Capturing an exercise job changes its durable state and explicitly records `deletedRows: 0`; the captured exercise leaves account data intact. The UI never offers a hosted delete action. `CustomerRetention.tickWorkspace(workspace)` reconciles scheduled cases with current-owner verification, fresh service facts and audit of changed cases. Repeated ticks leave reviewed versions stable. The capture clock derives from the server-owned billing exercise offset; live mode uses actual time.

## Separate erasure authority

`customer-retention/executor.ts` is an operator library and is absent from customer HTTP/MCP. It requires explicit enablement, an exact Flockletter database name, an exact restricted executor role, no superuser/BYPASSRLS privileges, private durable authorization and protected checkpoint verification. The authorization binds workspace, job, service source version, current manifest, protected checkpoint, operator and an expiry of at most one hour. Conflicting retries cannot replace it.

Provision that role separately; never give these grants to the application runtime. It needs schema usage, SELECT/DELETE on the reviewed public tenant manifest, UPDATE on the two retention case/job tables to acquire their row locks, INSERT on the immutable public receipt ledger, and SELECT/INSERT/UPDATE on the private control authorization and receipt tables. It also needs schema usage and SELECT/DELETE only for the exact private scheduler routing table; erasure removes that workspace’s route transactionally. The runtime has no DELETE grants and no private control-schema access. Executor authorization must be based on an independently authenticated operator session and exact approved target. A caller-supplied label alone is not authentication.

Before application-database erasure, independently verify current protected erasure/suppression checkpoints and reviewed disposition of provider/engine/export copies. `verifyExternalStores` and `verifyCheckpoint` are mandatory operator-supplied verification boundaries, not permission to return `true` for real customers without evidence. The executor rechecks current cancellation and the 90-day deadline, hold/job state and full protected table manifest, then deletes child tables first within a transaction and stores its minimal private receipt and a read-only public receipt that prevents a still-valid external organization from reinitializing erased application data. A replay returns that receipt. External copies are not claimed to have been deleted by the application transaction.

Hosted activation still needs real operator credentials, a protected external checkpoint store, external-copy inventory/erasure evidence, an approved restore operator and retention policy for minimal control receipts. These are configuration/operational gates; staging exposes the captured flow while they are absent.

## Recovery quarantine and evidence

The existing `scripts/retention-drill.ts` continues to create only its own disposable local cluster and accepts no hosted target. A stale snapshot is denied runtime connection before recovery. An independent sealed checkpoint carries erasure receipts and terminal suppression facts. Recovery reapplies erasure and opt-out evidence before restoring runtime access. The drill now populates every table in the enlarged manifest, including support, billing, audience, team and campaign delivery state; original populated-all-table and neighboring-workspace assertions remain intact.

`tests/customer-support.test.ts` verifies durable capture, cross-workspace/identity rejection, sensitive escalation, approved-facts-only AI input, changed-revision rejection, unknown-provider reconciliation and signed inbound replay/loop protection. `tests/customer-retention.test.ts` verifies the exact 90-day boundary, hold/reinstatement, explicit reviewed inventory, rejection of owner-hosted erasure, actual restricted-role disposable erasure and durable replay. `tests/retention-drill.test.ts` verifies all-table erasure, protected restore quarantine, later suppression replay, schema drift, complimentary and unverified closures. These are real disposable PostgreSQL checks, not hosted purge tests.

## Native inbox and bounded automation implementation

The November 9 completion adds FL-SUP-001/002, FL-ID-005 and FL-API-001/003 support paths without enabling live email. The existing internally signed envelope remains available as a separate bridge. Native Resend intake verifies the exact raw request with the provider's `svix-*` headers. Its signed metadata selects only a configured destination, then retrieves the matching email ID from the fixed Resend receiving endpoint. Unknown destinations are rejected before retrieval. Requests time out, redirects are forbidden, response reads stop at 64 KiB, and plain-text input is capped at 8,000 characters. HTML, raw MIME, attachments and their URLs are never fetched. See Resend's [native payload](https://resend.com/blog/inbound-emails), [retrieval response](https://resend.com/docs/api-reference/emails/retrieve-received-email) and [raw-body verification guidance](https://resend.com/docs/webhooks/verify-webhooks-requests).

A configured global mailbox sends normalized untrusted content only to a private platform triage port. Claiming a sender address never chooses a workspace or authenticates a customer. A server-owned address binding can create an escalated conversation, without customer permissions. Established conversations may receive replies through an expiring, opaque 192-bit address derived from a dedicated signing secret. The private routing registry exposes only guarded registration and exact-token lookup functions; the runtime cannot read or change its table. Registration requires the current initialized tenant and rejects replacement of a live route. A reply also needs the exact participant digest and receiving-provider DMARC pass; mismatches go to private quarantine. The thread path rechecks its participant and expiry inside the workspace transaction. Automatic-mail headers, common robot senders and mail with attachments cannot trigger an automatic reply.

Native receipt intent precedes retrieval for tenant-bound mail. Replayed accepted/ignored events return their original receipt without another fetch or conversation message. Provider failure preserves a pending receipt; at most five retrieval attempts are allowed before operator review. Changed signed metadata for an existing provider email ID is rejected. The platform triage port independently persists/deduplicates global and quarantined mail by provider ID and normalized digest. A missing triage port fails closed, so an unassigned message is not silently acknowledged and lost.

### Operator review and automation policy

`executeForOperator` is a server-only port. The separate platform layer must mint the immutable case reference after verified operator organization, server allowlist and fresh MFA checks, bound to the exact workspace, ticket/action or policy request. Browser/API input cannot create the grant. Each mutation rechecks its authority under the workspace lock and records actor, reason and case reference. This allows a platform operator to help a customer without making the operator the customer's workspace owner. The existing customer-owner boundary remains intact. A queued new provider submission rechecks original authority immediately before handoff. After an attempted submission becomes uncertain, the worker may perform read-only receipt reconciliation after operator authority expires; it never turns that expiry into a retry.

Automation is a distinct, versioned policy. An operator previews the exact selected public responses, approves their review code before its one-hour expiry, and publishes only if the prior policy version and public guidance digest remain current. Policies expire within 30 days; a later disabled policy stops new automatic work. Each response is either deterministic public guidance or an AI-assisted draft explicitly approved in that immutable policy. Arbitrary AI output is never promoted to approved guidance automatically. Live automatic support additionally requires separately approved server activation; it defaults off.

Only an exact recognized public-guidance question can match the deterministic topic gate. Sensitive words, uncertain wording, unverified intake, an unapproved topic and repeat automatic replies are held for a human. At most one automatic reply is attempted per conversation, with the existing five-total-reply bound. The automatic message identifies itself and offers a human handoff. Its decision and dispatch are durable, versioned, idempotent and visible in Support. Unknown provider results use lookup only. Automatic responses cannot perform account actions.

The optional OpenAI-compatible writer is disabled unless operator configuration explicitly enables an exact allowlisted origin and model. Plain HTTP is limited to loopback; remote use requires HTTPS and an explicit origin allowlist. Its fixed endpoint, fifteen-second deadline, bounded output and no-redirect behavior are independent of message content. Its only user-role input is approved public guidance; incoming questions, email addresses, workspace identifiers, credentials, customer records and conversation history never enter the prompt. Its output remains a disclosed draft until exact human policy/reply approval. No provider data-use or live-delivery approval is implied by configuring this adapter.
