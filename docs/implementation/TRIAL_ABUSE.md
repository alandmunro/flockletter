# Private trial eligibility and explicit activation

This implements FL-BIL-002/003/007, FL-ID-005, FL-DEL-005, FL-AUD-005 and FL-OPS-004 under D-042. It does not activate real billing or silently amend the accepted 90-day retention policy.

## Customer flow

1. A current verified Clerk workspace owner selects a plan. A private owner reservation lasts 35 minutes. Stripe Checkout expires after 31 minutes from the fresh provider request (at most two minutes after the saved intent) and collects a card in **setup mode only**. No subscription or charge is created by setup, redirect or setup webhook.
2. The original current owner requests `customerBilling.trialReview`. The server retrieves the completed Checkout, successful off-session SetupIntent and attached card from the authenticated Stripe account. Environment, workspace, intent, customer, card type and fingerprint must match. No browser field can establish card proof.
3. Review freezes a version, exact catalogue USD monthly price, 14-day duration, first-charge UTC date, setup revision, digest and ten-minute acceptance deadline. The UI explains cancellation and requires explicit acceptance. At acceptance the actual trial end is exactly 14 days from the server acceptance time, to whole seconds; a changed UTC first-charge date requires a new review.
4. `customerBilling.activateTrial` rechecks the original current owner and provider proof. It atomically consumes both the verified owner identity and provider card identity, saves the approval and durable activation intent, then creates the subscription under a stable idempotency key. An unknown response is looked up on retry; it never creates a second subscription speculatively. The durable approval commits before the provider boundary, then new provider requests and platform holds serialize on the same workspace lock. Read-only reconciliation remains available while held. If a crash or hold intervenes before the first POST and exhaustive lookup still finds no subscription, the explicit failure state requires support review rather than creating another agreement automatically.
5. Only a verified, account-bound provider event applies subscription eligibility. If the exact approved provider subscription is already known while its event is delayed, a current owner can open billing management/cancellation only after an independent exact subscription/customer/workspace check; that route grants no sending eligibility. Trial eligibility is rechecked by the same billing gate used before recipient dispatch. A reused card/owner produces a generic denial and no paid subscription. An explicitly accepted normal monthly paid Checkout is a separate command and requires its exact current integer price. Pending trial agreements cannot overlap a paid agreement.

No UI/API/MCP caller receives another workspace’s identity, card information, claim or existence. Existing pre-upgrade saved Checkout intents retain their original agreement and reconciliation path. Newly created ordinary Checkout intents are paid with zero trial days; fresh free enrollment uses the new setup path.

## Registry and failure states

The private `flockletter_customer_jobs` schema owns `trial_namespaces`, `trial_claims` and `trial_attempts`. Forced tenant RLS protects `customer_trial_setups`, the local provider mapping and approval. Runtime has no direct private-table permissions; its only registry function is `trial_claim(text,text,text,text,integer,integer,text,uuid,text,text,text)`.

Global identifiers are keyed HMAC-SHA256 values, **pseudonymous personal data, not anonymous data**. Separate labels hash verified Clerk user ID, provider-held card fingerprint and workspace. The namespace isolates provider account and exercise/test/live mode. Its stable digest does not depend on the HMAC key; a changed or missing key cannot create an empty namespace and refresh eligibility. Unknown key or policy history fails closed. Key rotation therefore requires a separately reviewed migration preserving uniqueness history; the ordinary UI/operator has no reset operation.

An advisory transaction lock serializes owner/card claims across workspaces. The same intent can replay only with the same owner, workspace and card. Reservations never extend on replay. An abandoned reservation expires; a new intent can recover after its deadline. A missing card-only Checkout can recover only after 36 minutes and an exhaustive authenticated lookup finds no session; the old request is never blindly submitted again. Setup requests prepared more than two minutes earlier are refused before POST, keeping the 31-minute provider session within the 35-minute reservation. At most three fresh owner reservations are allowed in a rolling 24 hours. A completed trial claim cannot be reset by workspace deletion, plan change, rejoin or another ordinary command. Reconciliation requires the original saved approval and provider facts; a webhook cannot create a recurring agreement.

## Explicit retention policy gate

Lifetime “one trial” uniqueness and deleting every identifying claim after 90 days cannot both be promised. No indefinite anti-abuse exception has been accepted by the owner. **Real provider free-trial activation remains disabled until a separate minimal keyed-claim retention exception is approved and configured.** This is a business policy activation gate, not an unfinished implementation. Ordinary paid service and existing saved agreements are not implicitly disabled by an unapproved new-trial policy.

Two explicit policy modes are implemented:

- `lifetime`: consumed owner/card/attempt records have no expiry. Requires an approved policy ID/version and stable HMAC key. Only this mode satisfies the current real-provider lifetime/no-refresh requirement. Hosted retention requires a signed exception binding the exact minimal inventory and policy; otherwise purge fails closed rather than silently retaining undocumented records.
- `bounded`: finite 1–3650-day claim retention, used only in an explicitly separate synthetic exercise namespace. Expiry is supported and disclosed as bounded-window protection. It does not satisfy or silently replace the live lifetime requirement. Expiring one synthetic customer never disables all other customers.

Minimal private record inventory: namespace/key tag; policy ID/version/mode/days; claim kind; owner/card/workspace keyed digest; intent UUID; reservation/consumed state; created timestamp and nullable expiry. No raw Clerk user ID, raw workspace ID, fingerprint, email, card number, address or mailing list is stored globally. Tenant mappings/approvals follow the hosted erasure inventory.

The operator-only `trial_retention_inventory(namespace,workspace_digest)` returns namespace, workspaceDigest, policyId, policyVersion, policyMode, retentionDays, recordCount, retainUntil and a SHA-256 digest of the canonical bounded row snapshot. Lifetime retainUntil is null. Zero rows remain a valid inventory. `trial_expire_claims(namespace,workspace_digest)` deletes **only records actually due by the database clock**, returns remaining inventory and never expires lifetime claims. Neither function is granted to runtime. The protected retention executor binds these facts to its reviewed exception manifest before tenant purge removes the scoped mapping. No public customer command can remove consumed eligibility records.

## Configuration

`trialRegistryFromEnvironment(env, source, account)` supplies `BillingOptions.trialRegistry`. The source/account must match the configured gateway; Stripe account retrieval verifies the actual account before card proof or provider mutation.

Hosted: `FLOCKLETTER_TRIAL_HMAC_KEY` (stable private secret, minimum 32 characters), `FLOCKLETTER_TRIAL_POLICY_ID`, positive `FLOCKLETTER_TRIAL_POLICY_VERSION`, and separately approved `FLOCKLETTER_TRIAL_RETENTION_APPROVED=true`. Also require `FLOCKLETTER_TRIAL_HISTORY_BASELINE=verified-empty` or `reviewed-backfill` after actual provider/history review. There are no secret, baseline or approval defaults. Existing saved legacy trials are not retroactively protected merely by enabling a fresh registry; a nonempty historical population requires a separately reviewed authoritative backfill. Baseline choice is bound into the stable versioned key tag and cannot silently change. Live billing retains all existing production activation gates.

Synthetic: `FLOCKLETTER_EXERCISE_TRIAL_HMAC_KEY`, optional `FLOCKLETTER_EXERCISE_TRIAL_POLICY_ID` (synthetic-v1), `_POLICY_VERSION` (1), `_RETENTION_DAYS` (90). Use source exercise and an explicit synthetic account. It never shares keys or eligibility with actual card facts. Existing legacy captured fixtures without a registry remain captured-only; hosted staging supplies the explicit registry to exercise cross-workspace protection. Production cannot enable captured billing.
