# Protected hosted retention operator

Implemented foundation for FL-AUD-005, FL-ID-005 and FL-OPS-005. This does not activate hosted erasure. No hosted customer data or remote objects were deleted while building it. Synthetic and injected AWS contract checks are identified separately from real provider evidence.

## Operator checklist

The local model drafted this checklist; chat reviewed it and corrected the ambiguous capture wording.

- Keep hosted erasure disabled until the owner approves its separate release.
- Use distinct runtime, read-only planning, destructive executor, and MFA-bound signing authorities. Runtime has no private-control table access. Signing keys never enter the executor.
- Verify a current signed checkpoint in the configured account, dedicated versioned bucket and exact workspace key, under S3 Object Lock COMPLIANCE retention. Compare its latest object version, sequence and digest with the signed approval.
- Review the exact current job, case version, service cancellation version, 90-day eligibility, hold, table inventory, external inventory and private-retention exceptions. Approval expires within 15 minutes and names one workspace/job/database.
- Obtain signed current external-copy inventory and a disposal receipt for every configured renderer instance, including offline/old hosts. One process's local pool is insufficient proof of global disposal.
- Explicitly review every retained anti-abuse policy/version/count/digest. A lifetime exception has `policyMode: lifetime` and `retainUntil: null`; this is deliberate retained data, never missing evidence or an implicit exception. D-048 accepts the minimal keyed lifetime trial-history policy; the live registry still requires verified key/policy configuration and real provider/history baseline. The exact signed exception inventory and independent hosted-purge authorization are not replaced by that policy decision.
- Journal exact external targets before mutation. Inspect unknown responses; do not blindly submit again. Unknown, blocked or unlisted copies stop application erasure.
- Keep restored snapshots offline. Reapply the latest protected suppression and quarantine facts before a separate operator release. Reconciliation never pretends restored application data has already been erased.
- Report captured checks as captured checks; they do not establish live-provider operation.

## Integration and configuration

`createHostedRetentionPlanner` reads owner-only absolute configuration/database files and a fixed owner-only inventory directory. The inventory filename is SHA-256 of `databaseName + NUL + workspaceId + NUL + jobId`, followed by `.json`. The artifact contains a purpose-signed current external inventory. The factory's distinct restricted planning role may read tenant inventory and the exact trial inventory function; it cannot delete or insert erasure authorizations. Planning derives current facts rather than accepting caller-provided target digests.

Planner configuration fields: `databaseName`, `plannerRole`, `inventoryKeys` (key ID to Ed25519 public PEM), and `checkpoint` containing `accountId`, `region`, `bucket`, `prefix`, `minimumRetentionMs`, `maxAgeMs`, `publicKeys`. Buckets must be dedicated `flockletter-*`; checkpoint prefixes are `retention/<name>/`. SDK clients use fixed official US regional endpoints, expected bucket owner and one attempt. No caller URLs are accepted.

`signRetentionApproval` runs only inside the separate MFA-bound platform authority after exact case review and trusted planning. Purpose-separated Ed25519 signatures prevent checkpoint/inventory seals from becoming destructive approvals. Capture-mode signatures are never accepted by live execution. Exact public-key allowlists are separate for approvals, inventory, checkpoints and engine receipts.

The separate operator executable is `node --import tsx scripts/retention-operator.ts` during development, or `node dist/server/server/customer-retention/operator-main.js` after building. It accepts no command arguments. Set `FLOCKLETTER_RETENTION_LIVE=enabled` explicitly, `FLOCKLETTER_RETENTION_CONFIG_FILE` to its owner-only config, and `FLOCKLETTER_RETENTION_DATABASE_FILE` to an owner-only file containing the separate executor connection. Submit the artifact object `{approval, externalInventory, engineReceipts}` on protected stdin. Never put database credentials, private keys or artifacts in shell arguments or logs. Standard output contains only completion/replay booleans; refusal output contains a static category.

Executor configuration additionally contains `executorRole`, `approvalKeys`, `inventoryKeys`, `engineKeys`, `expectedEngineInstances` and `stores`. Each S3 store is `{name, accountId, region, bucket, prefix}`; the external prefix is `customer-copies/<name>/`, followed by the server-derived workspace hash. Objects require immutable version IDs and SHA-256 checksums. All versions and delete markers are inventoried, including noncurrent versions. Every configured store is checked for unexpected remaining objects, even if the signed list is empty. Other storage/provider types intentionally fail closed until concrete adapters exist.

Engine receipts use domain `flockletter.retention.engine-disposal.v1` plus NUL and canonical JSON; payload fields are `version:1`, `scope`, `checkpoint`, `instanceId`, `bootId`, `createdAt`, `quiesced:true`, `processStopped:true`, `ownedDirectoriesRemoved:true`. The signing authority must independently establish host identity and actual owned-directory disposal. Receipts are short-lived, bind the current checkpoint and must exactly cover the configured instance roster. Neither the library nor a local renderer callback creates that global evidence.

`publishProtectedCheckpoint` records a durable private intent before a conditional checkpoint write. A lost response is reconciled against the latest signed object and never automatically retried. Only separately signed facts can be published. S3 IAM must prohibit unreviewed writers and retention/version deletion; Object Lock alone does not prevent an authorized writer from appending a replayed old document. Use this sequenced conditional publisher exclusively, and keep its write authority separate from runtime and restore credentials.

Migration 027 journals approvals, external/checkpoint operations and restored-workspace quarantine in the existing private control schema. For production use the [fixed role/database/object phases](PRODUCTION_RETENTION_BOOTSTRAP.md), preserving the separate database owner and migrator ownership boundaries. `scripts/retention-operator-grants.ts` remains an isolated/nonproduction SQL generator and refuses production. Neither generator connects or issues credentials; SQL application remains a separately protected release step. Apply object grants only after migrations and review exact role membership, existing grants and object ownership. Configure AWS roles separately; the executor must not obtain the MFA signing private key or capability to remove protected checkpoints.

## Recovery and refusal behavior

`reconcileRestoredWorkspace` requires the configured restricted restore identity. It loads current protected facts, locks the workspace, compares latest protected version again and reapplies suppressions only to matching tenant/brand/subscriber records. It writes an explicit private quarantine record, never a false public erasure receipt. Its result always requires an independent operator release. `public.flockletter_restore_blocked()` is a fixed-search-path SECURITY DEFINER boolean for service startup. `public.flockletter_retention_blocked(text)` checks private erasure/quarantine facts for the current tenant and denies mismatched tenant context. Runtime receives only EXECUTE on these minimal functions, no private schema privileges.

A `quarantined` checkpoint precedes destructive work and continues to block stale restoration if an operation stops halfway. An `erased` checkpoint is signed only after independently verifying the durable database receipt and complete disposal evidence. A released checkpoint is a separately reviewed recovery action, never a side effect of restore verification. Existing public tables are locked during final current-inventory and source/case checks; changes require a fresh review. Exact workspace locks also cover the external phase and coordinated customer/operator writers. Private scheduler/support routes and operator case records are counted and deleted. Only minimal platform approval-artifact rows are excluded from pre-publication counts to avoid approval self-invalidation; those rows are still deleted and their signed authority is independently preserved in the private approvals/history journal. Raw reasons and messages have no such exclusion. Completed external/checkpoint journals discard target metadata and retain its digest.

Static refusal categories distinguish disabled feature, wrong identity, invalid/untrusted/expired signature, changed plan/checkpoint, missing engine roster, unconfigured store, unexpected copy, missing private exception and unknown external/checkpoint outcome. A renewed MFA-signed approval may supersede an expired approval only for the identical freshly verified plan, with no submitting, unknown or completed operation. Prior authority is appended to immutable approval history. Partial or uncertain external work requires explicit operator reconciliation; a new signature cannot silently authorize a repeat.

## Evidence

Focused approval, checkpoint and external-operation tests use generated keys, injected fixed AWS command clients, synthetic targets and real disposable PostgreSQL. They establish software contracts, tenant separation and private/runtime denial. They do not establish live AWS account protection, actual hosted renderer disposal or an authorized customer purge. The protected restore test keeps two synthetic workspaces, reapplies only the targeted suppression, checks fixed function search paths and proves runtime cannot inspect or clear private quarantine.

Local model: initial type declarations and operator checklist draft. Chat: architecture, signatures, schema/grants, planner, adapters, journals, CLI, recovery, security review and tests. The local checklist's ambiguous “live capture prohibition” wording was replaced with an explicit evidence distinction. An initial local test draft attempt could not reach the local service through restricted command access; the documentation draft succeeded using approved local network access.

### Checkpoint lock and backup age

Set `minimumRetentionMs` from the oldest backup eligible for recovery, including exported copies, plus time for an operator to complete quarantine and reconciliation. Record the actual provider recovery range and the creation dates and expiry policy of separately retained exports before adopting a value. A provider plan limit alone does not establish the age of a usable Flockletter backup.

For new versions, the publisher requests COMPLIANCE retention until the signed creation time plus the allowed freshness window, the required remaining retention, and one minute of margin. A reader still checks the actual version's retention deadline and signature. Existing versions keep their original deadlines. If a version lacks sufficient remaining protection, a restore stays quarantined.

The managed Flockletter production database requires at least 14 days of remaining COMPLIANCE protection at verification. Set its checkpoint configuration to `minimumRetentionMs: 1209600000`. The production reader and publisher enforce this floor even with a shorter configured value. The production S3 bucket also defaults to 14 days of fixed Compliance retention for new object versions.
